# 🗺 План розвитку MaxuBot

Мета: бот-завантажувач, який **швидкий**, тягне файли **понад 50 МБ** і стабільно
працює в групах під навантаженням.

---

## 1. Головна розвилка: як зняти ліміт 50 МБ

Ліміт 50 МБ — це обмеження **хмарного Bot API Telegram**, а не aiogram.
Тому «замінити aiogram» саме по собі нічого не дасть. Є три шляхи:

### Варіант A — самохостнутий Bot API сервер ✅ (обраний)

Telegram офіційно роздає [telegram-bot-api](https://github.com/tdlib/telegram-bot-api)
сервер, який запускається поруч із ботом (окремий контейнер у docker-compose).
Бот підключається до нього замість `api.telegram.org`.

**Що дає:**
- 📦 Відправка файлів до **2 ГБ** (замість 50 МБ)
- ⚡ У режимі `--local` файли передаються **через файлову систему**, а не HTTP —
  віддача 500-мегабайтного відео займає секунди, бо немає повторного аплоаду
- 🔌 aiogram підтримує кастомний API-сервер з коробки (`TelegramAPIServer`) —
  зміни в коді: ~10 рядків у `main.py`
- Вся поточна логіка (хендлери, кнопки, альбоми) працює без змін

**Ціна:** потрібні `api_id`/`api_hash` з [my.telegram.org](https://my.telegram.org)
(разова дія, 2 хвилини) + один додатковий контейнер (~100 МБ RAM).

### Варіант B — MTProto-бот (Telethon / Pyrogram-форки) ❌

Теж дає 2 ГБ, але:
- повний переписон усіх хендлерів (інший API, інша модель подій)
- Pyrogram фактично покинутий (живі лише форки), Telethon живий, але
  документація для ботів слабша
- аплоад через MTProto **повільніший**, ніж локальний `--local` режим
  (файл реально ллється по мережі частинами + FloodWait'и)

Висновок: більше роботи, менше швидкості. Відхилено.

### Варіант C — гібрид (Bot API + MTProto-аплоадер лише для великих файлів) ❌

Складність двох стеків одночасно не окупається, поки варіант A закриває 2 ГБ.
Тримаємо в кишені на майбутнє (файли > 2 ГБ — але їх і Telegram не прийме).

## 2. Звідки береться швидкість

Швидкість «лінк → медіа в чаті» складається з 4 етапів. Оптимізуємо кожен:

### 2.1 Кеш file_id — найбільший виграш ⚡⚡⚡

Коли Telegram один раз прийняв файл, він повертає `file_id`, який можна
пересилати **миттєво і безкоштовно** в будь-який чат.

- Redis (або SQLite для простоти): `hash(нормалізований_url) → {file_id, тип, підпис}`
- Повторний лінк (той самий тікток скинули в 5 чатів) → відповідь за **<1 секунду**,
  без завантаження взагалі
- Нормалізація URL перед хешуванням: прибрати трекінг-параметри (`?igsh=…`, `?si=…`),
  розгорнути короткі лінки (`vm.tiktok.com`, `youtu.be`)
- TTL ~30 днів + інвалідація при помилці відправки

### 2.2 Швидше завантаження з джерела ⚡⚡

- **aria2c** як зовнішній завантажувач yt-dlp (`-x16 -s16`): багатопотокове
  скачування, для YouTube/довгих відео — прискорення в рази
- `concurrent_fragment_downloads: 8` для HLS/DASH фрагментів
- **Одна спроба замість «драбини» форматів**: спочатку `extract_info(download=False)`
  (метадані — це швидко), вибрати найкращий формат, що влазить у ліміт, за
  реальними розмірами з метаданих → одне завантаження замість 2–4
- Завантаження в **tmpfs** (`/dev/shm`) — нуль дискового I/O
- Для TikTok/Instagram/X — опційно **cobalt** (самохостнутий, окремий контейнер)
  як швидкий перший шлях, yt-dlp як надійний фолбек

### 2.3 Паралельність і черга ⚡

- Пул воркерів (asyncio, N=4–8) з чергою задач замість обробки «в лоб»
- Ліміти: на чат (1 активне завантаження), на користувача, глобальний
- Дедуплікація в польоті: якщо той самий URL уже завантажується для іншого
  чату — другий запит чекає результат першого, а не качає повторно
- `uvloop` замість стандартного event loop

### 2.4 UX швидкості

- Статусне повідомлення оновлюється прогресом («⏳ 45 % · 12 МБ/с»)
  з тротлінгом (раз на 2–3 с, щоб не впертись у флуд-ліміти)
- `send_chat_action` під час роботи
- Для великих файлів — чесна оцінка часу

## 3. Цільова архітектура

```
┌─────────────┐   webhook/polling   ┌──────────────────────┐
│  Telegram    │◄──────────────────►│  telegram-bot-api     │  (контейнер,
│  (юзери)     │                    │  --local, до 2 ГБ     │   спільний volume)
└─────────────┘                    └──────────┬───────────┘
                                              │ localhost / unix socket
                                   ┌──────────▼───────────┐
                                   │  maxubot (aiogram)    │
                                   │  ├─ хендлери          │
                                   │  ├─ черга задач        │
                                   │  └─ пул воркерів       │
                                   └───┬──────────┬───────┘
                                       │          │
                             ┌─────────▼──┐  ┌────▼─────────────┐
                             │  Redis      │  │  Завантажувачі    │
                             │  file_id-кеш│  │  yt-dlp + aria2c  │
                             │  черга/локи │  │  gallery-dl       │
                             └────────────┘  │  (cobalt — опц.)  │
                                             └──────────────────┘
                                   спільний tmpfs/volume для файлів
```

Все — один `docker-compose.yml`: `maxubot` + `telegram-bot-api` + `redis`.

## 4. Етапи реалізації

### Етап 1 — Великі файли (найбільша цінність) 🎯
- [x] Контейнер `telegram-bot-api` у docker-compose (`--local`, спільний volume)
- [x] aiogram → кастомний `TelegramAPIServer`, `.env`: `API_ID`, `API_HASH`, `BOT_API_URL`
- [x] Підняти `MAX_FILE_MB` до ~1950, прибрати зайві щаблі «драбини» якості
- [x] Відправка через локальний шлях до файлу (без HTTP-аплоаду)

**Результат:** відео до 2 ГБ, віддача великих файлів за секунди.

### Етап 2 — Кеш і миттєві повтори
- [x] Redis у compose; модуль `cache.py`: нормалізація URL → hash → file_id
- [x] Відправка з кешу перед будь-яким завантаженням
- [x] Дедуплікація завантажень у польоті (той самий URL паралельно — качаємо раз)
- [x] Інвалідація при `wrong file identifier`

**Результат:** популярні лінки віддаються < 1 с.

### Етап 3 — Швидкість завантаження
- [x] aria2c у Docker-образ + `external_downloader` у yt-dlp
- [ ] Вибір формату за метаданими замість перебору форматів
- [x] tmpfs для тимчасових файлів, `uvloop`
- [x] Черга з пулом воркерів + ліміти на чат/юзера
- [x] Прогрес у статусному повідомленні

**Результат:** типовий тікток/рілс — 2–5 с, YouTube 500 МБ — десятки секунд.

### Етап 4 — Стабільність і зручності
- [ ] Retry з бекофом на мережеві збої; окремі зрозумілі помилки
  (приватний пост / геоблок / потрібні cookies)
- [ ] Ротація cookies-профілів для Instagram; PO-токени для YouTube за потреби
- [ ] Вибір якості кнопками (наприклад, 360p/720p/1080p) для довгих відео
- [ ] `/stats` для адміна: кеш-хіти, час завантаження, помилки за платформами
- [ ] Webhook-режим замість polling (нижча латентність старту обробки)
- [ ] CI: тести + лінт на GitHub Actions

## 5. Ризики та як їх гасимо

| Ризик | Мітигація |
|---|---|
| Instagram ріже анонімні запити | cookies-профілі + gallery-dl фолбек + cobalt |
| YouTube 403/throttling на серверних IP | aria2c, ротація клієнтів yt-dlp (`android`/`ios`), PO-токени |
| Флуд-ліміти Telegram при відправці альбомів | тротлінг, черга відправки, retry після `RetryAfter` |
| Диск забивається великими файлами | tmpfs + ліміт розміру + гарантований cleanup у `finally` |
| Один чат «зʼїдає» всі воркери | пер-чатові ліміти в черзі |
